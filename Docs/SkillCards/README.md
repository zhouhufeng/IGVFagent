# Skill cards

A skill card is a machine-readable specification for one IGVFagent skill. The
set of cards is what makes the skill library consumable by software other than
this agent — a version-pinnable, inspectable contract rather than a feature of
one program.

```bash
igvfagent skillcard list                    # one line per skill
igvfagent skillcard show --skill mavedb     # one card, as JSON
igvfagent skillcard export                  # all cards + skillcards.json bundle
igvfagent skillcard coverage                # validation coverage (markdown)
```

`skillcards.json` is the bundle: one document, every card, suitable for another
agent or client to read.

## Everything is derived, nothing is asserted

Cards are generated from the running system, so they cannot drift from it:

| Field | Derived from |
|---|---|
| `id`, `title`, `module` | the CLI skill registry |
| `interfaces.tools` | the tool registry — the exact schemas the model is shown |
| `upstream_resources` | `_resolve_endpoint(...)` calls in the module source |
| `artefact_kinds` | the `Report:` / `Manifest:` / `Wrote:` lines it emits |
| `documentation` | `Docs/Skills/*.md` |
| **`validation`** | **which `Benchmarks/*/run.sh` actually invoke the skill** |

Regenerate with `igvfagent skillcard export`; there is no hand-maintained
source to fall out of date.

## The validation field

This is the field that answers "how is a skill's scientific validity
established", and it is derived rather than claimed. A card reports
`benchmarked` only when a benchmark in the suite executes that skill, and it
carries the evidence — the benchmark id, the paper's DOI and PMID, the number
of machine-checked criteria, and the path to the `run.sh` that does it.

```json
"validation": {
  "status": "benchmarked",
  "method": "machine-checked reproduction of published results",
  "evidence": [
    { "benchmark": "waters2024_bap1",
      "paper": { "journal": "Nat Genet", "year": 2024,
                 "doi": "10.1038/s41588-024-01800-z", "pmid": "38969834" },
      "checks": 5,
      "run": "Benchmarks/waters2024_bap1/run.sh" }
  ],
  "n_checks": 13,
  "scope_note": "Benchmarks execute fixed command sequences with no model in
                 the loop, so this establishes implementation correctness only."
}
```

**`unvalidated` is a real status, not a gap in the metadata.** It means no
benchmark executes that skill. It does not mean the skill is wrong — most
unvalidated skills are retrieval wrappers whose correctness is largely
self-evident at the API boundary. But saying so explicitly is the point: a
consumer can decide for itself which skills it is willing to depend on.

Current coverage — see [`COVERAGE.md`](COVERAGE.md), regenerated by
`igvfagent skillcard coverage`:

| | |
|---|---|
| Skills | 48 |
| Benchmarked | 16 (33%) |
| Unvalidated | 32 |
| Machine-checked criteria | 61 |

`scope_note` restates the limit that applies to all of it: benchmarks run
fixed command sequences with the model removed, so they establish that
implementations are correct, not that an agent would select them unaided. See
[`Docs/EVALUATION.md`](../EVALUATION.md).

## Using a skill from another agent

Each card carries the full typed interface, so an external system can call an
IGVF skill without importing IGVFagent's runtime:

```python
import json, subprocess
cards = json.load(open("Docs/SkillCards/skillcards.json"))
card  = next(c for c in cards["skills"] if c["id"] == "mavedb")

tool = card["interfaces"]["tools"][0]
tool["parameters"]          # JSON Schema — register directly with your model
tool["subcommand"]          # e.g. "mavedb map"  -> igvfagent mavedb map ...

subprocess.run(["igvfagent", *tool["subcommand"].split(), "--urn", "..."])
```

`version` pins the card to a release, and `upstream_resources` names the
external archives the skill depends on — so a consumer can tell, before
running anything, what a skill will contact and what will break if an archive
changes.

## Adding a skill

New skills appear automatically once registered in the CLI skill registry;
export regenerates the bundle. A skill authored at a user's request through
`igvfagent extauthor write-skill` is registered the same way and receives a
card on the next export, with status `unvalidated` until a benchmark exercises
it.

## Limitations

- **Validation coverage is derived from benchmark execution, not from
  scientific review.** A `benchmarked` skill reproduced a published result at
  some point; it is not a statement that the method is appropriate for a given
  question.
- **`last_confirmed` is not yet populated.** Cards say which benchmark
  validates a skill, not when that benchmark last passed. Wiring in
  `Benchmarks/results/` would close this and is the obvious next step.
- **Upstream versions are named, not pinned.** `upstream_resources` records
  which archives a skill contacts, not which release of each — so a card
  cannot yet tell you that an archive changed underneath a validated result.
