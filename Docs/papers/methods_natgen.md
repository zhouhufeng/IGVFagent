# Methods

**Software design and implementation.** IGVF Agent is implemented as a single Python package (Python ≥3.9) and released under the Apache-2.0 licence. The command-line interface, the agent runtime, the graphical and programmatic interfaces and the library of analytical skills share one code path. An analysis step therefore executes identically whether it is invoked by an investigator, by a script or by the language model. The base package has no third-party dependencies. Analytical functionality is distributed as optional modules that rely on established scientific libraries, including NumPy, pandas, SciPy, scikit-learn, AnnData, Scanpy[ref], PyArrow, DuckDB, CVXPY[ref] with the SCIP solver[ref] and NetworkX, so a deployment installs only what its workflows require. All required dependencies are permissively licensed; two optional clustering libraries (leidenalg and python-igraph) are distributed under the GNU General Public License and are installed only on request.

**Tool library.** Every capability was first implemented as an explicit command and only then exposed to the language model as a tool. Each tool is defined by a name, a natural-language description and a typed parameter schema that maps directly onto the command's arguments. The current release defines 613 tools spanning data discovery, retrieval, knowledge-graph queries, assay-specific processing pipelines, statistical analyses and visualization. Because the full library exceeds the context budget of smaller models, a deterministic selector exposes at most 128 tools per query. The selector gives priority to tools already used in the session, then to tool families matched by domain vocabulary, then to tools ranked by inverse-document-frequency-weighted lexical overlap between the query and each tool description, and finally to designated entry-point tools. Selection depends only on the query text, so every model is offered the same tools for the same question.

**Agent runtime.** The runtime implements an iterative plan–act–observe–evaluate loop. Before the model is consulted, structured identifiers in the query are recognized by rule and routed to the matching tool: IGVF or ENCODE accessions and portal URLs to the dataset description tool, dbSNP identifiers to the variant lookup, genomic intervals to the region query and gene symbols to the gene query. The deterministic results of these calls seed the conversation. At each iteration, the model receives the accumulated transcript together with the tool schemas, and either requests one or more tool calls or returns an answer. Planning is thus interleaved with execution rather than fixed in advance. Requested tools are executed as separate operating-system processes of the command-line interface. Their exit status, output streams and the file paths of any artefacts they report are captured, and a condensed record is returned to the model.

The loop terminates when the model answers without requesting further tools, when an iteration budget (default 8) is exhausted, or when the run stalls. A run is considered stalled when the same set of tool calls with identical arguments recurs, or every call in an iteration fails, for three consecutive iterations. After an exhausted or stalled run, the model is queried once more without tools to summarize the evidence gathered. Sampling temperature and decoding seed default to zero. The final answer is assembled from a deterministic skeleton, listing the commands executed and the artefacts produced, followed by the model's narrative summary. Consequently, two models that execute the same plan return answers whose factual sections are identical.

Every run is persisted with its complete transcript, the artefacts produced, the iteration and tool-call counts, failed calls, the reason for termination, and the model and backend used. Each tool invocation is additionally logged to a local provenance store with its inputs, outputs and timestamp. A session can therefore be replayed command by command without the language model.

**Language-model backends.** A single tool-calling interface dispatches to thirteen backends. These comprise the Anthropic Messages API, which is used with native tool use; OpenAI-compatible chat-completion interfaces with function calling, covering both hosted services (OpenAI, Groq, Together, DeepInfra and Hugging Face) and locally served open-weight models (Ollama, vLLM and Text Generation Inference); and the Claude Code and Codex command-line agents, which exchange tool calls through a fixed structured protocol. The backend is chosen by the user, by an environment setting or from the model name, and defaults to a locally served open-weight model. Tool selection, identifier routing and answer assembly are independent of the backend, so analysis code is unchanged when the model is replaced.

**Configuration, credentials and data security.** The 42 external services contacted by the agent are addressed through endpoints resolved at runtime. These include the IGVF and ENCODE portals and the IGVF Catalog, GEO, CELLxGENE, the Human Cell Atlas, Zenodo, MaveDB, Ensembl and UniProt. Each endpoint has an encoded default that can be overridden by an environment variable, allowing a single installation to target public services, development instances or local mirrors. The encoding is not a security measure; it ensures only that no endpoint is hard-wired into the source code. Credentials are read exclusively from the runtime environment or from local files excluded from version control, and are never stored in the code base. These include portal access keys, knowledge-graph credentials, Synapse access tokens and model-provider keys. This separation allows the deployed software to be released publicly without modification and to operate inside institutional environments that host controlled-access genomic data.

**Local data storage and provenance.** Retrieved and derived data are stored locally in a layered architecture. A Bronze layer holds the mirrored knowledge graph as compressed Parquet files queried through DuckDB. A Silver layer is an analytical DuckDB warehouse into which skills deposit curated tables, together with records of each ingest (the generating command, its arguments, start and end times, rows written and outcome). Analytical outputs are additionally written to time-stamped, per-analysis directories. Downstream analyses run against these local tables without further access to the source archives.

**Cross-archive survey of single-cell multiome data.** We surveyed publicly available single-cell multiome datasets, with paired transcriptome and chromatin-accessibility measurements, across six repositories. From the IGVF Data Portal we retrieved analysis sets annotated as 10x Multiome, 10x Multiome with MULTI-seq or SHARE-seq, and from the ENCODE Portal released experiments and series matching multiome terms. GEO series were identified through the NCBI E-utilities with six multiome search phrases, and their supplementary-file listings were then parsed. CELLxGENE Discover collections were selected by multiome assay labels or the corresponding Experimental Factor Ontology terms, Human Cell Atlas projects by paired RNA and ATAC library-construction approaches in the Azul data browser, and Zenodo records by the same search phrases used for GEO. Results were harmonized into a single manifest recording, for each file, the source repository, dataset and file accessions, data type, file format, size, download location and checksum. Files were assigned by filename rules to nine categories: RNA count matrices, ATAC count matrices, fragment files, peak sets, cell annotations, alignments, index files, raw sequencing reads and other files. Sizes were taken from repository metadata. GEO supplementary listings do not report file sizes, so GEO datasets were included in the inventory but excluded from aggregate volume estimates. Retrieval is selective: users filter by data type and accession pattern, and the total download volume is reported before any transfer. **[The complete survey required approximately N minutes on a standard workstation and indexed N datasets, N files and N TB; confirm against the run reported in Results.]**

**Local mirror of the IGVF knowledge graph.** The IGVF Catalog knowledge graph[ref] (58 collections; 25 document and 33 edge collections) was mirrored by streaming each collection through the read-only query-cursor interface of its ArangoDB database. Each collection was written as compressed Parquet files (zstd). To accommodate collections whose documents differ in size by orders of magnitude, the batch size was set from each collection's mean document size to bound responses at approximately 64 MB. Batches doubled in size after eight consecutive successes and halved on server or rate-limit errors. Transient failures were retried up to six times with exponential backoff, and per-collection checkpoints allowed interrupted transfers to resume without loss.

The six largest collections together contain 11.1 billion records, including 1.87 billion variants and 5.93 billion variant–variant relationships. These were partitioned into key ranges of approximately 25 million records and retrieved in parallel. Each completed collection was registered as a DuckDB view, after which all queries ran offline; collections already mirrored are available for querying while the largest collections continue to download. **[The complete mirror occupies approximately N TB compressed.]**

**Network inference.** Signed causal networks were inferred with the CARNIVAL formulation[ref], reimplemented as a mixed-integer linear program in CVXPY from its published mathematical description, without reuse of source code from existing implementations[ref CORNETO]. Given a signed prior-knowledge network, a set of perturbed nodes with known signs and a set of measured nodes with observed signs and weights, the program assigns each node an activity state of activated, inhibited or inactive, and selects a subset of edges. Constraints require that a selected activating edge transmits the state of its upstream node and a selected inhibitory edge inverts it, that every active, non-perturbed node is explained by at least one selected incoming edge, and that perturbed nodes retain their imposed state. The objective minimizes the weighted discordance between predicted and observed states at measured nodes, plus a sparsity penalty proportional to the number of selected edges (β = 0.2). Programs were solved with SCIP[ref]. Inferred networks are stored in the analytical warehouse with their provenance.

**Reproduction of published studies.** Published analyses were reproduced through a closed loop driven by a packaged agent skill. First, a citation, DOI, PubMed or PubMed Central identifier, or free-text description was resolved to a single publication by querying Crossref, Europe PMC, PubMed, OpenAlex, Semantic Scholar and bioRxiv. Candidates were scored on title (weight 0.55), authors (0.20), journal (0.15) and publication year (0.10). A publication was accepted when its score was at least 0.85 and exceeded that of the next candidate by at least 0.15.

The full text was retrieved from Europe PMC or the preprint server. Accessions for data and code repositories, including GEO, SRA, IGVF, ENCODE, Synapse, MaveDB, figshare, Zenodo, ArrayExpress, PRIDE, CELLxGENE and GitHub, were extracted together with their textual context. Accessions in dbGaP and the European Genome–phenome Archive were flagged as controlled access. The headline results of each study were enumerated as a set of analyses, one per main figure panel or quantitative claim. Each analysis recorded the paper's statement, its reported value and the authors' source files that produce it.

The authors' code was obtained at a pinned commit and executed without modification in a reconstructed software environment, and its outputs served as the reference. Where the code could not be executed, the authors' deposited intermediate results or source data served as the reference instead. Each analysis not already supported by IGVF Agent was reimplemented in Python, preserving the authors' algorithm, parameters, filters and random seeds. Registering a new command required explicit authorization, a pinned commit of the source repository, the upstream source files and a module that passed static checks. Each port was recorded with its provenance and a checksum, and was marked as unreviewed until inspected by a person. Each port was executed on the same input as the reference and compared value by value. A value was considered concordant when the absolute difference was at most 10⁻⁸ plus 10⁻⁶ times the reference value. Concordance was computed over all reference values, so values absent from the port counted as discordant. A port was accepted when at least 99% of values were concordant. Accepted ports became permanent commands available to the agent in subsequent analyses.

Each check was classified as quantitative agreement with a value reported in the paper (class A), agreement of a port with the authors' code (class B), a retrieval or enumeration count (class C) or the generation of an artefact (class D). An analysis was considered reproduced only when a confirmed class A or class B check tied to it passed. Analyses supported only by class C or D checks were classified as weak. Analyses requiring controlled-access, embargoed or undeposited data were classified as blocked, with the supporting evidence recorded. A study was classified as reproduced when all of its analyses were reproduced, and as reproduced except for access when every remaining analysis was blocked. The loop continued until one of these states was reached, or until each remaining analysis was blocked or had failed after repeated attempts. For every analysis not reproduced exactly, the agent recorded the specific data or code that would resolve the discrepancy, for communication to the authors.

For the three studies shown in Fig. 4 (Liu et al.[ref], Gschwind et al.[ref] and Pan et al.[ref]), every value quoted in the paper was compared with the reproduced value, and agreement within 5% was considered concordant. Figure panels supported by deposited data were redrawn and compared with the published panels. **[The benchmark comprises N studies; reconcile with the benchmark table.]**

**Model-independence of results.** Two procedures assessed whether results depend on the choice of language model. First, pinned playbooks specify a fixed, ordered sequence of tool invocations that execute without the model, which is consulted only to write a closing summary. These produced identical analytical artefacts across backends, differing only in the narrative text. Second, an evaluation harness submitted the same query to several backends under a common system prompt, seed and tool set. For each pair of runs it reported the Jaccard similarity of the artefacts produced, the term-frequency–inverse-document-frequency cosine similarity of the final answers, and the differences in iteration and tool-call counts (Supplementary Fig. 1).

**User interfaces.** IGVF Agent is accessible through a command-line interface, an interactive shell, a web application and a Model Context Protocol server that exposes the tool library to external agent clients. Eight packaged skills encode recurrent multistep workflows as reusable instructions: variant interpretation, GWAS locus dissection, gene dossiers, regulatory landscapes, disease-gene mapping, cross-population linkage-disequilibrium comparison, faceted portal search and reproduction of published studies.

**Statistics and reproducibility.** No statistical method was used to predetermine sample size. Statistical tests within reproduced analyses followed the original studies and are reported with the corresponding results. Concordance thresholds for reproduced values (5%) and for ports against reference code (relative tolerance 10⁻⁶; 99% concordant values) were set before scoring. Language-model runs used temperature 0 and a fixed seed. All analyses can be re-executed from the recorded command transcripts.

**Data availability.** All data analysed in this study are publicly available from the IGVF Data Portal (https://data.igvf.org), the IGVF Catalog (https://catalog.igvf.org), the ENCODE Portal (https://www.encodeproject.org), GEO, CELLxGENE Discover, the Human Cell Atlas Data Portal and Zenodo, under the accessions listed in Supplementary Table **[N]**. Data for the reproduced studies were obtained from the deposits cited by those studies (figshare 26299093; the Supplementary Tables of Gschwind et al.; the Source Data of Pan et al.). No new data were generated.
